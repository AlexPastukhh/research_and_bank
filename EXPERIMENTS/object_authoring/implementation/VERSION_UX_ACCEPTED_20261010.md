# Применение рекомендаций о версиях и обычной работе

Record ID: VUX-20261010-01. Дата: 2026-10-10.
Основание: пользователь принял рекомендации PR-001 и PR-003 после независимой проверки модели версий. Исходная проверенная версия: Git HEAD `33905bebf3a406278c39288479b8fa1171b014d8`.

## Краткий результат / Для пользователя

PR-001 и PR-003 реализованы: обычный интерфейс показывает материалы по названию, редакторы работают с материалом, а полные ID и документ доступны через «Технические детали». Неизменённая форма показывает «Изменений нет» и не начинает подготовку.

Внутренняя модель версий, первое сохранение, закреплённые ссылки, конфликт STALE_BASE, точный повтор и сохранённые файлы остаются прежними. Предположение о том, что большинство материалов останутся в первом состоянии, не используется для специальной ветки хранения.

Проверка: регрессия из 52 случаев и повторная проверка изменённых мест завершены; у каждого проверенного случая последний результат PASS, пропусков нет. Это составное доказательство, а не один полный прогон финального исходника. Локально: синтаксис всех Python-файлов и четыре независимые проверки действительных методов с собственными входами прошли. Локальный контейнер не имеет jsonschema; интеграционные проверки выполнены проектным Python на Windows.

Визуальная приёмка пользователем остаётся открытой. При следующем запуске стоит проверить формы и «Технические детали»; полный отчёт читать не требуется. Ни исправление прежнего владельца реального search-cache, ни завершение FUB10/OBJ10/OBJ11 этим изменением не объявляются.

Карта документа: «Принятые решения» фиксирует точный scope; «Что изменилось в интерфейсе» описывает обычную работу; «Проверки и ограничения» содержит проверяемые доказательства; «Review Log» сохраняет состояние для продолжения.

## Что изменилось в интерфейсе

- Основные разделы: «Материалы», «Коллекции», «Поиск». История открывается явной командой. Поиск по умолчанию использует актуальные материалы, история добавляется явным флажком.
- Строки показывают тип, название и время сохранения. Список истории/поиска получает названия по точному pin на существующем worker, не на потоке Tk.
- «Редактировать», «Добавить заметку», «Добавить выбранный материал», «Другой файл» и «Выгрузить файл» описывают действие без терминов object/base/revision/original.
- Технические ID, исходный документ и квитанция доступны по запросу. Представление не меняет данные, ссылки и их identity. Подготовленные записи с одинаковым названием различаются номером строки; операция использует полный ID из модели.
- Технические детали открытой формы показывают захваченную базу, а выбор другого материала её не меняет.

Проверка «Изменений нет» выполняется после сбора редактируемых полей, до отправки команды в worker и до создания транзакции. Учитываются название, данные (включая тело, ссылки и порядок), редактируемое происхождение. Технические producer/IDs/времена не считаются правкой. Новый материал и явный выбор другого файла продолжают обычную подготовку; смена данных с возвратом к исходному вводу её пропускает. Backend по-прежнему допускает явное создание revision: no-op policy находится на границе редактора, не в механизме хранения.

## Стоимость и совместимость

Scenario operation: пользователь не вводит ID и не выполняет лишнюю подготовку для неизменённой формы. Другие стадии сохранения не объединены. Названия истории/поиска требуют не более 10 дополнительных закреплённых чтений на страницу; время зависит от Bank и файловой системы, количественная delta unknown. Это отображение, не изменение поиска или head-selection.

Realization: только представление, редакторная проверка, тесты и навигационная документация. DDL, canonical read/search schemas, importer, сохранённые документы, профиль первой/последующих записей не меняются. Локальная и Windows-копии сверены по hash; перед применением проверены прежний HEAD и hash каждого изменяемого файла. Существующие файлы сохранены в отдельной резервной копии перед заменой.

Lifecycle: форматирование объединено в presenter; обычные списки и контекст используют его. Ограниченный кеш названий использует полный tuple, а не название как identity. Удаление модели версий не предлагалось; специальные исключения для первой записи не добавлены. Deadline и бюджет разработки не установлены; календарных гарантий нет.

После первой регрессии изменился только formatter `render`; остальные runtime functions идентичны. Повторные проверки покрывают formatter и исправленные новые тесты.

- Windows регрессии используют собственные временные Banks. UI-проверка использует собственный withdrawn Tk; она подтверждает управление виджетами, но не пользовательское восприятие/визуальную приёмку.

Две последующие ошибки новых проверок также были ошибками входных фикстур и разрешены с повторной проверкой. Это ограничения прежних попыток проверки, не обнаруженные дефекты приложения.
- Прежняя проблема реального search-cache с владельцем Administrators и нулевым размером не изменялась. Тесты используют собственный cache; результат не доказывает работоспособность поиска в пользовательском Bank с тем владельцем.
