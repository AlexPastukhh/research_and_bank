# R1 bounded Bank read API — synthetic component

Task R1-BANK-READ-API-001; local development then guarded native transfer. No installed real Bank, search/UI or release claim.

The closed local-bank-query/1 request schema is unchanged. Five operations are implemented: bank.get, collection.get, bank.original, bank.history, receipt.get. bank.search fails UNSUPPORTED_MODE until its separate card. Operator-supplied --bank-root and --output-root are trusted app configuration, not request fields. Read requests on stdin and exactly one bounded JSON response on stdout; exit 0 for OK, 2 for ERROR. Never create/initialize a Bank, import intake, fetch a locator or execute media. Native Python venv is PLANNING/TOOLS/.schema_validation_env/Scripts/python.exe.

Example on the authorized Windows machine (existing synthetic test DB paths only until deployment is separately accepted):

    <venv-python> <repo>/EXPERIMENTS/bank_read_api/bank_read.py --bank-root <configured-existing-private-root> --output-root <configured-private-export-root>

Send one valid BANK_QUERY.schema.json request through stdin. New private test roots are created only by the test suite, never by the read API. Both configured roots must already exist, be trusted/private and not overlap. BANK_UNAVAILABLE means unavailable, not an empty/new Bank. Current selects one read snapshot and returns a pinned ref. History pages use explicit durable commit sequence; null resolves once, later pages pass returned snapshot_sequence. Paging uses indexed object history and limit+1 rows, no global history materialization or total COUNT scan. Selected documents, original bytes and canonical receipts are verified against retained manifest/hash/rows. Unrelated large BLOBs are not read for a document get; receipt.get verifies its bounded whole accepted command. Collection preserves exact membership/order and returns direct member availability; no latest substitution/recursive expansion. Missing/corrupt direct members remain present and explicitly unavailable.

LIMITS.json defines request 16KiB/depth16, response4MiB, retained metadata64MiB, total stored work264MiB, direct members256, SQL VM2M steps and elapsed30sec per request. A valid large collection or page exceeding a budget fails LIMIT_EXCEEDED, without truncation/partial OK; callers can request smaller history pages. Supplemental result.schema.json closes envelopes and operation output fields, while existing document and receipt schemas validate canonical payloads. No request, object or physical-schema version was changed.

Original bytes are copied to exclusive app-owned <exports>/<random-UUID>/original.bin, streamed SHA/length-checked and readback-verified before OK. Display filename is metadata only. Windows API context holds protected read handles against mutation; close/CLI exit releases handles. Accepted exports remain private disposable files, with returned hash/length; later consumers must verify these values rather than assuming a perpetual lock. No automatic output deletion or cleanup of canonical Bank content. Failed or unpublished exports are reclaimed. HTML/media is opaque bytes, never executed/rendered by this API. Locator-only result is metadata without network/file fetch.

The current writer does not persist diagnostic attempt receipts. receipt.get returns original canonical ACCEPTED receipt and actual hash, with latest_diagnostic_attempt.availability=not_recorded_by_current_writer. It never fabricates a latest failure or treats missing receipt as proof the command failed. Bounded indexed attempt lookup/recording is a future write-path task. Logical read-only operation may invoke existing bounded SQLite-owned hot-journal rollback before opening its final readonly transaction; it does not write canonical application rows or delete journals manually.

Run test_reads.py for portable/native evidence. Linux uses the explicit trusted fixture adapter, with no Windows confinement claim. Windows uses actual secure-reader snapshots, NTFS private roots, ACLs and protected export handles. TEST_HISTORY and ISSUES preserve failures/corrections/retests. REVIEW_LOG.json preserves card review; native evidence/acceptance remains pending until NATIVE_RESULTS.json and completion receipt are verified.
