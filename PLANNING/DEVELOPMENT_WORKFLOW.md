# Работа над системой и приложением — порядок разработки

Обновлено: 2026-10-08; история процедуры с 2026-10-05 сохранена. Это процедура vNext development, не новый router или принятый release contract.
Маршрут выбирается по принятому CORE/USE_CASE_REGISTRY.json; workflow не заменяет его.
Актуальная задача определяется только блоком `CURRENT_WORK_ITEM` в [SESSION_STATE.md](SESSION_STATE.md).
Workflow не хранит отдельную текущую карточку; исторические ссылки ниже не являются указателями продолжения.

## Один цикл

| Шаг | Действие | Сохраняемый результат |
|---|---|---|
| 1. Восстановить контекст | Читать SESSION_STATE, карточку, её inputs; проверить изменения другого чата | Актуальные входы и ограниченная задача |
| 2. Привязать к плану | Requirement IDs, один UC, milestone, отдельные system/app results | Карточка; отсутствие app delivery фиксируется явно |
| 3. Ответить до работы | Записать вопросы, решения и источники; возникшие вопросы дописывать | Нет скрытых blocking решений |
| 4. Изменить | Проверить исходные hashes/diff; править только разрешённые файлы; сохранить резервную копию | Reviewable diff и сохранённая история |
| 5. Проверить и принять | Проверки по критериям задачи и релевантным осям; показать evidence каждого критерия | Результат done или blocked; tests PASS сами по себе не закрывают задачу |
| 6. Оставить checkpoint | Результат, изменённые файлы, команды/exit codes, остаток, один следующий шаг | Карточка + короткий указатель в SESSION_STATE |

Статус задачи хранится в её карточке; SESSION_STATE указывает на неё и содержит контекст продолжения.
План релизов хранит обязательства поставки. Закрытие одной карточки не закрывает gate/milestone автоматически.
Критерии новой задачи нужно задавать под её результат, а не копировать из примера механически.

## Передача в новый чат

Достаточное стартовое указание:
«Продолжи C:\Users\alexa\research_and_bank. Прочитай PLANNING/SESSION_STATE.md,
найди блок CURRENT_WORK_ITEM, прочитай указанную там карточку и required_inputs.
Проверь её status: completed — не команда повторить задачу; awaiting_user_answers — не разрешение
подставить ответы пользователя. Выполни разрешённую неблокированную часть одной ограниченной задачи,
сохрани evidence, checkpoint и следующий шаг. Работай SNAPSHOT-FIRST + TUNNEL VERIFY через Туннель app://asdk_app_6ac4ae16f7e081919a02522c365b34bb».

Не требуется восстанавливать чат или делать commit/push для локального продолжения.
Перед применением пакетно проверить актуальные hashes HOST; читать заново только отсутствующие или изменившиеся входы. При drift пересобрать diff, не затирать конфликтующие изменения пользователя.
Если отдельный Tunnel-вызов не отвечает 25 секунд, прекратить ожидание и сообщить неопределённый результат вызова.
После timeout записи сначала проверить её фактический результат; слепо повторять запись нельзя.
Production/runtime research требует соответствующих TaskManifest, RunState и typed outputs;
эта development-карточка не подменяет эти контракты.

## Обновление актуального указателя

При завершении шага обновить единственный блок CURRENT_WORK_ITEM в SESSION_STATE и добавить исторический checkpoint.
Карточку завершённого шага и её next_action не переписывать как новую задачу. Новый шаг получает отдельную карточку.
CURRENT_WORK_ITEM указывает реальную незавершённую карточку; её status и blocking вопросы читаются перед mutation.
Если указатель/карточка противоречат друг другу, сначала восстановить актуальную связь с evidence; не выбирать последнюю историческую ссылку автоматически.

## Текущий пользовательский workflow — 2026-10-08

Решение: USER_SNAPSHOT_FIRST_TUNNEL_WORKFLOW_2026-10-08.json. Оно заменяет старое указание Remote Desktop Commander в шаблоне передачи задачи. Исходный текст сохранён в ../EXPERIMENTS/full_target_review/20261008_033045/first_bank_card_review/WORKFLOW_BEFORE.md.

SNAPSHOT — основная среда массового чтения, поиска, анализа, сравнения, редактирования, генерации, экспериментов и локальных проверок. HOST через выбранный Туннель — источник актуального состояния, место применения готового результата и проверки настоящего runtime/процессов/служб ОС. Это относится также к документации, конфигурациям, данным и ассетам; Git не обязателен.

Получить недостающий актуальный набор одним архивом/экспортом, выполнить целостную итерацию локально, затем переносить минимальный patch. Если большой набор нельзя получить разумным пакетным вызовом, запросить у пользователя snapshot/архив. Не использовать HOST как удалённый диск для промежуточных итераций. Независимые незаблокированные части продолжать.

Перед переносом: сверить свежие hashes HOST и allowed paths, сохранить backup/history, не перезаписывать конфликтующие изменения. После переноса: подтвердить bytes/hashes, runtime и нужную интеграцию в настоящем окружении; записать команды, PID, exit codes, ограничения и receipt. Неизвестный результат mutation после timeout сначала проверить, повторный запуск допустим только после установления фактического состояния.

GUI основного desktop ради подтверждения не открывать. При необходимости визуальной приёмки пользователь открывает указанное окно, проверяет конкретные элементы и при необходимости предоставляет screenshot. Headless-проверки не закрывают визуальный gate.

Завершение означает целостный результат в snapshot, подтверждённое применение с сохранением пользовательских изменений, реальные применимые проверки и отсутствие известных расхождений. Документационный шаг подтверждает сохранение документов, а не готовность ещё не реализованного приложения.
